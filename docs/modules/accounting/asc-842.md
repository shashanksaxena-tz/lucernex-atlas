# ASC 842 — classification and measurement surface

**Stated up front.** Lucernex implements ASC 842 classification as **five pass/fail tests on one
record**, `ContractFinancialTest`. The polarity is inverted from how the standard is usually written:
**pass = operating, fail = finance**, and *any single failure* makes the lease a finance lease. The
vendor states it plainly on all five test fields: *"If you 'fail' at least one of the five tests, the
lease will be classified as a Finance lease. If you 'pass' all tests, the lease will be considered an
Operating lease."* Three of the five tests are user-asserted checkboxes; two are computed
threshold comparisons. The result is written to `ContractFinancialTest.FinalResult`, and only a
**locked** test propagates to `Contract.LatestFinancialTestFinalResult`.

*Evidence class for this page: **Observed** unless a paragraph says otherwise. Source for every
vendor quotation is `_xlsx_lucernex_jcrew.txt`, sheet `Field Inventory`, column `Definition`
(identical text also appears in `_xlsx_feature_list.txt`). Field types are from
`docs/data-fields/contract-financial-test.md` and `docs/data-fields/all-fields.csv`.*

## The five tests

| # | The question | Input field | Type | How the result is produced | Result field |
|---|---|---|---|---|---|
| 1 | Does ownership of the asset revert to the tenant at the end of the lease term? | `DoesTitleRevertToTenant` | `sTYPE_CHECKBOX` | User assertion. Vendor: *"This check box is Test 1 of the ASC 842 test."* | `Test1Result` (`sTYPE_PASS_FAIL`) |
| 2 | Does the lease contain a purchase option the tenant is likely to exercise? | `ContainsBargainPurchaseOption` | `sTYPE_CHECKBOX` | User assertion. Vendor: *"This check box is Test 2 of the ASC 842 Test."* | `Test2Result` (`sTYPE_PASS_FAIL`) |
| 3 | Is the lease term a major part of the asset's remaining economic life? | `ComputedTestTermLengthToRemainingLife` vs `RemainingEconomicLifeThreshold`; override `IsLeaseNearEnd` | `sTYPE_PERCENTAGE` vs `sTYPE_PERCENTAGE`; `sTYPE_CHECKBOX` | **Computed.** Vendor: *"The value of this field is the Term Length (based on Test) divided by the Remaining Economic Life. The comparison of this percentage to the Remaining Economic Life Threshold determines the pass / fail value displayed for the Test 3 result."* | `Test3Result` (`sTYPE_PASS_FAIL`) |
| 4 | Does the PV of lease payments amount to substantially all of the fair value of the portion controlled? | `InitLiabilityBalToThreshFairValueCtrld` vs `ThresholdFairValueControlled` | `sTYPE_PERCENT_MATH_OPERATION`, `sTYPE_MONEY_MATH_OPERATION` | **Computed.** Vendor: *"If you exceed your Threshold Fair Value Controlled, your Test #4 result will be 'Failed'."* | `Test4Result` (`sTYPE_PASS_FAIL`) |
| 5 | Is the asset so specialized that the lessor will have no alternative use for it? | `IsAssetTooSpecializedForLessor` | `sTYPE_CHECKBOX` | User assertion. Vendor: *"This check box is Test 5 of the ASC 842 Test."* | `Test5Result` (`sTYPE_PASS_FAIL`) |

`ContractFinancialTest.FinalResult` (`sTYPE_TEXT`) holds the verdict. Vendor: *"The final result of
the ASC 842 test. If you 'failed' at least one of the five tests, your lease is considered a Finance
lease. If you 'passed' all five tests, your lease is considered an Operating lease."*

### The Test 3 and Test 4 arithmetic, exactly as documented

```
Test 3
  ComputedTestTermLengthToRemainingLife = TestTermLength / RemainingLife
  Test3Result = Pass  if  ComputedTestTermLengthToRemainingLife < RemainingEconomicLifeThreshold
              = Pass  if  IsLeaseNearEnd = true          # unconditional override
              = Fail  otherwise
  RemainingEconomicLifeThreshold is "usually set to 75%"           (vendor)
  RemainingLife is expressed in CodeRemainingLifeFreqUnitID units  (weeks / months / years)

Test 4
  FairValueControlled          = FairValueOfAsset * PortionOfAssetControlled
  ThresholdFairValueControlled = FairValueControlled * FairValueThreshold
  InitLiabilityBalToThreshFairValueCtrld
                               = InitialLiabilityBalance / ThresholdFairValueControlled
  Test4Result = Fail if InitialLiabilityBalance > ThresholdFairValueControlled
  FairValueThreshold is "usually set to 90%"                       (vendor)
```

The `IsLeaseNearEnd` override is explicit and unconditional: *"If this check box is selected, Test 3's
outcome will change to Pass regardless of whether the value the Test Term Length to Remaining Life
field is greater than the Remaining Economic Life Threshold field."*

**Note the asymmetry a rebuild must preserve:** Test 4's numerator is `InitialLiabilityBalance` —
which field exactly? `ContractFinancialTest` holds `ASC842InitialLiabilityBalance` *and*
`IFRS16InitialLiabilityBalance` *and* an `InitialLiabilityBalanceAdjust`, and the vendor text for
`ThresholdFairValueControlled` says the comparison is against *"your Initial Liability Balance
(Adjusted)"*. Whether the adjusted or unadjusted ASC 842 figure feeds the test is **not** resolvable
offline. See open questions.

## Term length: three different lengths, three different fields

This is the subtlest part of the record and the easiest thing to get wrong in a rebuild.

| Field | Type | Meaning |
|---|---|---|
| `TermLength` | `sTYPE_DATE_MATH_OPERATION` | *"the term length of your lease based upon the difference between the Commencement Date and the Expiration Date"* — the contractual term |
| `LikelyTermLength` | `sTYPE_DATE_MATH_OPERATION` | *"If you have marked any terms as Likely on the Abstract Info > Terms page, this field will calculate the length of your likely term"* — the reasonably-certain term |
| `TestTermLength` | `sTYPE_DATE_MATH_OPERATION` | *"the length of the test term that you have selected using the Test Begin Date and Test End Date fields"* — the term actually used in Test 3 |

`LastLikelyOptionDate` carries *"the end date of the last likely term"*, sourced from the Terms page.
The "Test Begin Date" and "Test End Date" fields named in the `TestTermLength` definition **do not
exist anywhere in the schema** — the nearest candidates are `Topic842BeginDate` / `Topic842EndDate`
(labelled "Accounting Begin Date" / "Accounting End Date"). Whether they are the same fields under a
later label is an open question.

`ContractTerm.CodeTermStatusID` is the code table that presumably carries the "Likely" status, and
`ContractTerm.IncludeTermForAccruals(Boolean)` is a second, separate inclusion switch — a term can be
included for accruals without being marked likely, or the reverse. *(**Inferred** from field names;
the Term Status code values are not in any offline artifact.)*

## The measurement surface

`ContractFinancialTest` computes **two complete parallel measurements**, one per standard. The
`ASC842*` and `IFRS16*` field pairs are identical in definition text — the vendor definitions for
`ASC842InitialAssetBalance` and `IFRS16InitialAssetBalance` are the same string.

| Concept | ASC 842 field | IFRS 16 field | Type | Vendor definition |
|---|---|---|---|---|
| Cash value of the lease, before adjustments | `ASC842CalcAggValOfLeaseNoAdj` | `IFRS16CalcAggValOfLeaseNoAdj` | `sTYPE_MONEY` | *"the cash value of the lease between the accounting begin date and end date"* |
| Cash value of the lease, after adjustments | `ASC842CalcAggValueOfLease` | `IFRS16CalcAggValueOfLease` | `sTYPE_MONEY` | *"…with accounting assumption adjustments"* |
| PV of financial terms, before adjustments | `ASC842CalcPVOfFinTermsNoAdj` | `IFRS16CalcPVOfFinTermsNoAdj` | `sTYPE_MONEY` | *"the present value of your financial terms as of your accounting begin date, prior to any accounting assumption adjustments"* |
| PV of financial terms, after adjustments | `ASC842CalcPVOfFinancialTerms` | `IFRS16CalcPVOfFinancialTerms` | `sTYPE_MONEY` | *"…after accounting assumption adjustments"* |
| Initial asset balance | `ASC842InitialAssetBalance` | `IFRS16InitialAssetBalance` | `sTYPE_MONEY_MATH_OPERATION` | *"the asset balance as of the accounting begin date"* |
| Initial liability balance | `ASC842InitialLiabilityBalance` | `IFRS16InitialLiabilityBalance` | `sTYPE_MONEY_MATH_OPERATION` | *"the liability balance as of the accounting begin date"* |
| Net lease liability | `ASC842NetLeaseLiabilityBalance` | `IFRS16NetLeaseLiabilityBalance` | `sTYPE_MONEY_MATH_OPERATION` | *"the cash value of lease payments plus any adjustments due to covenants"* |

A single, standard-agnostic `PVOfFinancialTermsWithAdjustments` (`sTYPE_MONEY_MATH_OPERATION`) also
exists: *"the present value of your financial terms minus any accounting assumption adjustments added
to the Accounting Assumption Adjustments table."* Note the vendor says *minus* here and *with* in the
per-standard fields — the sign convention is not consistent in the documentation.

## Locking, auto-computation, and propagation

| Field | Type | Behaviour |
|---|---|---|
| `AutoComputed` | `sTYPE_CHECKBOX` | *"This field will have a true value if the ASC 842 test was computed automatically by the system."* |
| `IsLocked` | `sTYPE_CHECKBOX` | *"Once you are certain that the results of your ASC 842 Test are correct, select this check box. Locking the test ensures that the test cannot be modified. You cannot delete a classification test once it has been locked, but you can create another test as necessary."* |
| `Contract.LatestFinancialTestFinalResult` | `sTYPE_TEXT` | *"The final result of the **most recently locked** ASC 842 test."* |

**Derived**: a contract accumulates many `ContractFinancialTest` rows over its life; only locked ones
are authoritative; there is no delete path once locked; superseding is by creating a new test. This is
an append-only, immutable-once-locked audit chain and should be rebuilt as one.

## Schedule types and what they enumerate

`CodeASC842Schedule` is a tenant-defined code table with 24 columns, of which exactly three are
semantic and 20 are GL account slots:

| Column | Type | Purpose |
|---|---|---|
| `ShortName` | Text | The value shown in the dropdown |
| `ActualLongName` | Text | Long description |
| `Inactive` | Boolean | Soft-delete |
| `DontAmortizeAssetValue` | Boolean | **The only behavioural switch on the whole table** — suppresses ROU-asset amortization for schedules of this type |
| `ExportAcct1Number` … `ExportAcct20Number` | Text ×20 | GL account numbers. Vendor: *"Export Accounts are tied to GL accounts in your Enterprise Resource Planning (ERP) System."* |

So an "ASC 842 Schedule Type" is, mechanically, **a named GL account mapping plus one amortization
switch**. The twenty account numbers are copied onto every `SLPeriod` row as
`ExportAcct1Number`…`ExportAcct20Number`, denormalized at generation time.

Which slot means which GL account is **not** in the schema — the columns are numbered, not named.
That mapping is pure tenant convention and is the first thing to establish before any ERP export can
be rebuilt.

### ⚠ This tenant has exactly one ASC 842 schedule type

**Observed**, 2026-09-10, `FirmCodeEdit.jsp?TableType=2162`:

| Type | Description | Don't Amortize Asset Value | Inactive |
|---|---|---|---|
| `842 Rent` | 842 Rent | no | no |

One row. The sibling tables are both empty: `Straight Line Schedule Type Code` (2161) and
`IFRS 16 Schedule Type Code` (2163) each return "No rows to display".

Three things follow:

1. **There is one set of twenty GL slots in play, not a matrix.** The open question below shrinks
   from "which slot means what, per schedule type" to a single row to read. That is a materially
   easier migration than the schema suggested.
2. **`DontAmortizeAssetValue` is unchecked on the only configured row.** Whatever it does, it is
   **not doing it in this tenant** — so `ACC-R-030`, the one rule in this module resting on a field
   name alone, cannot be validated against ASG's data at all.
3. **Every cash flow routes here.** With the other two tables empty,
   `CodeExpenseType.CodeSLScheduleID` and `.CodeIFRS16ScheduleID` have nothing to point at, so every
   expense type's routing (`ACC-R-025`) resolves to `842 Rent`.

*(Source: `docs/data-model/code-table-registry.md`.)*

### How a cash flow reaches a schedule type

`CodeExpenseType` carries all three routing FKs:

```
CodeExpenseType.CodeSLScheduleID     → CodeSLSchedule
CodeExpenseType.CodeASC842ScheduleID → CodeASC842Schedule
CodeExpenseType.CodeIFRS16ScheduleID → CodeIFRS16Schedule
```

Vendor, on `ExpenseAccrualSetup.CodeExpenseTypeID`: *"Expense Types are used to associate records with
lease accounting schedules, AP export numbers, expense accrual accounts, percentage rent accrual
accounts, and real estate tax accounts."*

**Derived**: the expense *type* — not the expense record, not the contract — decides which accounting
schedule a cash flow lands in, and therefore which GL accounts it exports to. Change one expense
type's `CodeASC842ScheduleID` and every schedule that uses it flips to `NeedsRecalculation = Yes`
(see `ACC-R-020` in [`rules.md`](rules.md)).

The same three FKs appear on `AcctingAssumptionAdjust`, `Covenant` and `ContractFinancialTest`, so an
adjustment or covenant can be steered to a *different* schedule from the base rent. That is how
Lucernex supports a single contract carrying two schedules under the same standard.
`AcctingAssumptionAdjust.SecondaryRentSchedAllocPercent` and
`Covenant.SecondaryRentSchedAllocPercent` split an amount across a primary and secondary schedule.

## Remeasurement and modification in the schema

Lucernex does not model a modification as an event record. It models it as **a new `SLSummary` that
carries deltas against the one it replaces**, and marks the old one inactive.

| Field on the new `SLSummary` | Vendor definition |
|---|---|
| `PriorLastPostedPeriodID` | *"populaes with the SLSummary ID for the previous accounting schedule when a new schedule is created"* [sic] |
| `PostedEndDate` | *"The last posted fiscal period End Date of the schedule being modified."* |
| `PostedInitAssetAdj` | *"The difference between the Initial Asset Balance of the new schedule and the previous schedule's posted Asset Balance as of the Posted End Date."* |
| `PostedInitLiabilityAdj` | *"The difference between the Initial Liability Balance of the new schedule and the previous schedule's posted Liability Balance as of the Posted End Date."* |
| `PostedAssetAdjustment` | *"The difference between the Asset Balance of the new schedule and the previous schedule's last posted Asset Balance."* |
| `PostedLiabilityAdjustment` | *"The difference between the Liability Balance of the new schedule and the previous schedule's last posted Liability Balance."* |
| `BalanceForward` | *"The difference between the asset and liability balance at the start of your accounting schedule."* |
| `RemeasurementBalanceForward` (label: **Balance Sheet Impact**) | *"The portion of the balance forward that does appear on the balance sheet going forward."* |
| `ProfitAndLossImpact` | *"The portion of the balance forward that will not persist on the balance sheet and is taken as a capital gain or loss."* |
| `Inactive` (on the **old** summary) | *"This flag is applied to a schedule if another lease accounting schedule replaces it."* |
| `InactiveDate` | *"The date that a schedule became inactive."* |
| `CodeScheduleCreationReasonID` | *"Select the reason the lease accounting schedule was created from this field."* |

So `BalanceForward = RemeasurementBalanceForward + ProfitAndLossImpact` — the carried balance is split
between what stays on the balance sheet and what is recognised in P&L. **Derived** from the two
definitions; the arithmetic is not stated explicitly.

### Mid-period remeasurement

Two fields exist purely to split a period at a remeasurement date:

- `InterestBeforeMidRemeasure` — *"The partial interest from the start of the period to the
  remeasurement date."*
- `SleBeforeMidRemeasure` — *"The partial single lease expense from the start of the period to the
  remeasurement date."*

### Term shortening

Four fields handle an early-termination remeasurement specifically:

| Field | Vendor definition |
|---|---|
| `ShortenedSchedInitLiabilityBal` | *"An initial Liability Balance based on the remaining periods of the original schedule over a shortened term."* |
| `ShortenedLeaseLiabilityDiff` | *"…minus the original schedule's last posted period's Liability Balance."* |
| `ShortenedTermAssetDiff` | *"The sum of the Asset Amortization Expense for the remaining periods in the original schedule over the shortened term multiplied by negative one."* |
| `ShortenedTermRentDiff` | *"The Initial Liability Balance of the new schedule minus the Initial Liability Balance of the remaining periods in the original schedule over the shortened term."* |

## The roll-forward disclosure

25 `SLSummary` fields in the `Contract / Roll Forward Report` subgroup, gated by
`IsIncludeInRollForwardReport(Boolean)`. **None of the 25 has a vendor definition** — they are the
least-documented block in the module. Their names describe a standard ASC 842 asset/liability
roll-forward:

```
PriorPeriodGrossAssetBalance / PriorPeriodAccumulatedAmortizationBalance / PriorPeriodLeaseLiability
  + NewGrossAssetBalances / NewLeaseLiabilities                       (leases commencing)
  + RemeasurementGrossAssetBalanceImpact
      / LeaseRemeasurementAccumulatedAmortizationImpact
      / LeaseRemeasurementLeaseLiabilityImpact                        (remeasurements)
  + ReclassificationOfGrossAssetBalance
      / ReclassificationAccumulatedAmortizationImpact
      / ReclassificationLeaseLiabilityImpact                          (operating ↔ finance reclass)
  + ReclassGrossAssetBalanceImpact
      / ReclassAccumulatedAmortizationImpact
      / ReclassLeaseLiabilityImpact                                   (a second, unexplained reclass set)
  - LeaseExpirationGrossAssetBalance
      / LeaseExpirationAccumulatedAmortizationImpact                  (expirations)
  - AssetAmortizationExpense / LeaseLiabilityPaymentImpact
  ± ImpairmentsAndAccumulatedAmortizationReset
  = EndingGrossAssetBalance / EndingAccumulatedAmortizationBalance / EndingLeaseLiabilityBalance
```

*Evidence class: **Inferred**. The roll-forward arithmetic above is reconstructed from field names
alone. Two near-duplicate reclassification triples exist (`Reclassification*` and `Reclass*`) and
nothing offline explains the difference. This block must be confirmed against a live report before
being rebuilt.*

## The schedule is reviewed and approved before it counts

*Added 2026-09-10. **Observed** in the running tenant at build `26.08.0.46`; full capture in
[`../layouts-and-forms/forms-vs-pages-vs-layouts.md`](../layouts-and-forms/forms-vs-pages-vs-layouts.md).*

Nothing in the offline schema shows this, because `SLSummary` carries only `IsApproved`. In the live
tenant, generating a schedule does not publish it — a three-step workflow named
**"ASC 842 Schedule Review/Approval"** does:

| # | Step | `Type` | `Approval Level` | Bound form layout |
|---:|---|---|---|---|
| — | (submission) | Form | — | `ASR Submit ASC 842 Schedules` |
| 1 | Initial Review of ASC 842 Schedules | Form | Member | `ASR Initial Review of ASC 842 Schedule` |
| 2 | Approve ASC 842 Schedules (ASG) | Form | Member | `ASR Approve ASC 842 Schedules (ASG)` |
| 3 | Approve ASC 842 Schedules (Client) | Form | Member | `ASR Approve ASC 842 Schedules (Client)` |

The form type carries sequence prefix `ASR` and declares attachability per entity kind: `Portfolio`
and `RE Contract` are `Yes`; `Capital Program`, `Prototype`, `Location`, `Parcel`, `Site`, `Project`,
`Facility`, `Capital Project` and — ⚠ — **`Equipment Contract`** are all `No`.

Three things follow for a rebuild:

1. **The ASC 842 measurement is a candidate, not a published result.** `SLSummary.IsApproved` is the
   terminus of a human chain, and it is documented as irreversible once set.
2. **Two parties sign off**, ASG then client. A single-approver design is the wrong process.
3. **Equipment leases have no route through this gate**, yet they produce ASC 842 schedules — `Asset`
   carries the full classification field set and `Contract.GenerateFASBSchedule` exists on equipment
   contracts. Unresolved; see open questions.

See `ACC-R-060`, `ACC-R-061`, `ACC-R-062`.

## The legacy Cap Lease Test on `Contract`

A **different, older** five-test structure lives directly on `Contract` and is still populated.

| Field | Type | Vendor definition |
|---|---|---|
| `Test1Result` … `Test4Result`, `Test5aResult`, `Test5bResult` | `sTYPE_TEXT` (not `PASS_FAIL`) | *"This field contains result N of the Capital Lease test for the contract."* |
| `FinalResult` | `sTYPE_TEXT` | *"The final result of the ASC 842 test."* — the label says ASC 842 even though the subgroup is Cap Lease Test |
| `DoesTitleRevertToTenant`, `ContainsBargainPurchaseOption` | `sTYPE_CHECKBOX` | Tests 1 and 2 |
| `RemainingLife`, `YearBuilt` | `sTYPE_NUMBER`, `sTYPE_DROPDOWN_YEAR` | *"This field appears in Test 3 of the Capital Lease Test."* |
| `FMVOfBuilding`, `FMVOfLand`, `FMVSource`, `BaseYearOperatingExpenses`, `BaseYearOtherExpenses`, `BaseYearRETax`, `AggregateNNNBaseRentNPV`, `LeasedLandArea`, `ProjectLandArea` | mixed | *"This field is included in Test 4 of the Capital Lease Test."* |
| `RatioTermAutoRenewToLife`, `RatioTermBargainRenewToLife`, `RatioLeaseAutoRenewToFMV`, `RatioLeaseBargainRenewToFMV` | `sTYPE_PERCENTAGE` | **Dead.** *"This is a legacy field that was used in the Capital Lease Test. It is no longer used, and does not impact the test."* |
| `AutomaticRenewalInLease`, `AutomaticRenewalOption`, `BargainRenewalInLease`, `BargainRenewalOption` | `sTYPE_CHECKBOX` | **Dead.** *"This field is not implemented for contracts or equipment contracts."* |

Differences from `ContractFinancialTest` that matter:

1. The Cap Lease Test splits Test 5 into **5a and 5b**; the ASC 842 test has a single Test 5.
2. Cap Lease Test 4 is land/building-value based (`FMVOfBuilding` + `FMVOfLand`, net of base-year
   expenses, against `AggregateNNNBaseRentNPV`); ASC 842 Test 4 is
   `InitialLiabilityBalance` vs `FairValueControlled × FairValueThreshold`.
3. Cap Lease results are free `sTYPE_TEXT`; ASC 842 results are `sTYPE_PASS_FAIL`.
4. Cap Lease Test has no lock, no `AutoComputed`, no per-standard measurement, and no child record —
   it is a flat block of columns on `contract_admin`.

**Derived**: this is the ASC 840 capital-lease test, retained for history. A rebuild should carry the
*data* forward for audit but should not implement the *logic*. Confirm with the client whether any
report still reads it.

## Open questions

Ranked by how much they block a rebuild.

1. **(new) ⚠ How does an equipment-lease ASC 842 schedule get approved?** The review workflow's form
   type excludes `Equipment Contract` (`ACC-R-061`), yet equipment leases generate schedules. Either
   they bypass the gate or they are approved at portfolio level.
2. **(new) What does each of the four `ASR` form layouts collect?** They define the approval record
   ASG Edge+ must reproduce, and none has been opened.
3. **(new) What happens on rejection at step 2 or 3?** No rollback or re-open path is documented and
   `SLSummary` has no "rejected" representation.
4. **What are the values of the `Schedule Creation Reason Code` table?** It is the only field that
   records *why* a schedule exists (initial, remeasurement, modification, reclassification,
   impairment, term shortening…). Without the enumeration, the schedule-version chain cannot be
   replayed. Check `Admin > Manage Firm Drop Downs`.
5. **Does ASC 842 Test 4 compare the adjusted or unadjusted initial liability?** The vendor text says
   *"Initial Liability Balance (Adjusted)"* on `ThresholdFairValueControlled` but names the field
   plainly as `InitialLiabilityBalance` on `Test4Result`. Open an ASC 842 Test on a contract with a
   non-zero `InitialLiabilityBalanceAdjust` and read the on-screen comparison.
6. **Do "Test Begin Date" / "Test End Date" exist in the UI as distinct fields from
   `Topic842BeginDate` / `Topic842EndDate`?** `TestTermLength`'s definition names them; the schema
   does not contain them.
7. **What distinguishes `Reclassification*` from `Reclass*` in the roll-forward block?** Six fields,
   two triples, no definitions.
8. **Which impairment input wins** when `SLSummary.ImpairmentAmount`,
