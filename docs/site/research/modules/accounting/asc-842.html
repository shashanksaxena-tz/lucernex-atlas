ASC 842 — classification and measurement surface

Stated up front. Lucernex implements ASC 842 classification as five pass/fail tests on one record, ContractFinancialTest. The polarity is inverted from how the standard is usually written: pass = operating, fail = finance, and any single failure makes the lease a finance lease. The vendor states it plainly on all five test fields: "If you 'fail' at least one of the five tests, the lease will be classified as a Finance lease. If you 'pass' all tests, the lease will be considered an Operating lease." Three of the five tests are user-asserted checkboxes; two are computed threshold comparisons. The result is written to ContractFinancialTest.FinalResult, and only a locked test propagates to Contract.LatestFinancialTestFinalResult.

Evidence class for this page: Observed unless a paragraph says otherwise. Source for every vendor quotation is _xlsx_lucernex_jcrew.txt, sheet Field Inventory, column Definition (identical text also appears in _xlsx_feature_list.txt). Field types are from docs/data-fields/contract-financial-test.md and docs/data-fields/all-fields.csv.

The Test 3 and Test 4 arithmetic, exactly as documented

Test 3
  ComputedTestTermLengthToRemainingLife = TestTermLength / RemainingLife
  Test3Result = Pass  if  ComputedTestTermLengthToRemainingLife < RemainingEconomicLifeThreshold
              = Pass  if  IsLeaseNearEnd = true          # unconditional override
              = Fail  otherwise
  RemainingEconomicLifeThreshold is "usually set to 75%"           (vendor)
  RemainingLife is expressed in CodeRemainingLifeFreqUnitID units  (weeks / months / years)

Test 4
  FairValueControlled          = FairValueOfAsset * PortionOfAssetControlled
  ThresholdFairValueControlled = FairValueControlled * FairValueThreshold
  InitLiabilityBalToThreshFairValueCtrld
                               = InitialLiabilityBalance / ThresholdFairValueControlled
  Test4Result = Fail if InitialLiabilityBalance > ThresholdFairValueControlled
  FairValueThreshold is "usually set to 90%"                       (vendor)

The IsLeaseNearEnd override is explicit and unconditional: "If this check box is selected, Test 3's outcome will change to Pass regardless of whether the value the Test Term Length to Remaining Life field is greater than the Remaining Economic Life Threshold field."

Note the asymmetry a rebuild must preserve: Test 4's numerator is InitialLiabilityBalance — which field exactly? ContractFinancialTest holds ASC842InitialLiabilityBalance and IFRS16InitialLiabilityBalance and an InitialLiabilityBalanceAdjust, and the vendor text for ThresholdFairValueControlled says the comparison is against "your Initial Liability Balance (Adjusted)". Whether the adjusted or unadjusted ASC 842 figure feeds the test is not resolvable offline. See open questions.

This is the subtlest part of the record and the easiest thing to get wrong in a rebuild.

LastLikelyOptionDate carries "the end date of the last likely term", sourced from the Terms page. The "Test Begin Date" and "Test End Date" fields named in the TestTermLength definition do not exist anywhere in the schema — the nearest candidates are Topic842BeginDate / Topic842EndDate (labelled "Accounting Begin Date" / "Accounting End Date"). Whether they are the same fields under a later label is an open question.

ContractTerm.CodeTermStatusID is the code table that presumably carries the "Likely" status, and ContractTerm.IncludeTermForAccruals(Boolean) is a second, separate inclusion switch — a term can be included for accruals without being marked likely, or the reverse. Schedule types and what they enumerate

CodeASC842Schedule is a tenant-defined code table with 24 columns, of which exactly three are semantic and 20 are GL account slots:

ColumnTypePurpose
ShortNameTextThe value shown in the dropdown
ActualLongNameTextLong description
InactiveBooleanSoft-delete
DontAmortizeAssetValueBooleanThe only behavioural switch on the whole table — suppresses ROU-asset amortization for schedules of this type
ExportAcct1Number … ExportAcct20NumberText ×20GL account numbers. Vendor: "Export Accounts are tied to GL accounts in your Enterprise Resource Planning (ERP) System."

So an "ASC 842 Schedule Type" is, mechanically, a named GL account mapping plus one amortization switch. The twenty account numbers are copied onto every SLPeriod row as ExportAcct1Number…ExportAcct20Number, denormalized at generation time.

Which slot means which GL account is not in the schema — the columns are numbered, not named. That mapping is pure tenant convention and is the first thing to establish before any ERP export can be rebuilt.

⚠ This tenant has exactly one ASC 842 schedule type

One row. The sibling tables are both empty: Straight Line Schedule Type Code (2161) and IFRS 16 Schedule Type Code (2163) each return "No rows to display".

Three things follow:

  1. There is one set of twenty GL slots in play, not a matrix. The open question below shrinks from "which slot means what, per schedule type" to a single row to read. That is a materially easier migration than the schema suggested.
  2. DontAmortizeAssetValue is unchecked on the only configured row. Whatever it does, it is not doing it in this tenant — so ACC-R-030, the one rule in this module resting on a field name alone, cannot be validated against ASG's data at all.
  3. Every cash flow routes here. With the other two tables empty, CodeExpenseType.CodeSLScheduleID and .CodeIFRS16ScheduleID have nothing to point at, so every expense type's routing (ACC-R-025) resolves to 842 Rent.

How a cash flow reaches a schedule type

CodeExpenseType carries all three routing FKs:

CodeExpenseType.CodeSLScheduleID     → CodeSLSchedule
CodeExpenseType.CodeASC842ScheduleID → CodeASC842Schedule
CodeExpenseType.CodeIFRS16ScheduleID → CodeIFRS16Schedule

Vendor, on ExpenseAccrualSetup.CodeExpenseTypeID: "Expense Types are used to associate records with lease accounting schedules, AP export numbers, expense accrual accounts, percentage rent accrual accounts, and real estate tax accounts."

Derived: the expense type — not the expense record, not the contract — decides which accounting schedule a cash flow lands in, and therefore which GL accounts it exports to. Change one expense type's CodeASC842ScheduleID and every schedule that uses it flips to NeedsRecalculation = Yes (see ACC-R-020 in rules.md).

The same three FKs appear on AcctingAssumptionAdjust, Covenant and ContractFinancialTest, so an adjustment or covenant can be steered to a different schedule from the base rent. That is how Lucernex supports a single contract carrying two schedules under the same standard. AcctingAssumptionAdjust.SecondaryRentSchedAllocPercent and Covenant.SecondaryRentSchedAllocPercent split an amount across a primary and secondary schedule.

The roll-forward disclosure

25 SLSummary fields in the Contract / Roll Forward Report subgroup, gated by IsIncludeInRollForwardReport(Boolean). None of the 25 has a vendor definition — they are the least-documented block in the module. Their names describe a standard ASC 842 asset/liability roll-forward:

PriorPeriodGrossAssetBalance / PriorPeriodAccumulatedAmortizationBalance / PriorPeriodLeaseLiability
  + NewGrossAssetBalances / NewLeaseLiabilities                       (leases commencing)
  + RemeasurementGrossAssetBalanceImpact
      / LeaseRemeasurementAccumulatedAmortizationImpact
      / LeaseRemeasurementLeaseLiabilityImpact                        (remeasurements)
  + ReclassificationOfGrossAssetBalance
      / ReclassificationAccumulatedAmortizationImpact
      / ReclassificationLeaseLiabilityImpact                          (operating ↔ finance reclass)
  + ReclassGrossAssetBalanceImpact
      / ReclassAccumulatedAmortizationImpact
      / ReclassLeaseLiabilityImpact                                   (a second, unexplained reclass set)
  - LeaseExpirationGrossAssetBalance
      / LeaseExpirationAccumulatedAmortizationImpact                  (expirations)
  - AssetAmortizationExpense / LeaseLiabilityPaymentImpact
  ± ImpairmentsAndAccumulatedAmortizationReset
  = EndingGrossAssetBalance / EndingAccumulatedAmortizationBalance / EndingLeaseLiabilityBalance

Evidence class: Inferred. The roll-forward arithmetic above is reconstructed from field names alone. Two near-duplicate reclassification triples exist (Reclassification* and Reclass*) and nothing offline explains the difference. This block must be confirmed against a live report before being rebuilt.

The schedule is reviewed and approved before it counts

Added 2026-09-10. Observed in the running tenant at build 26.08.0.46; full capture in ../layouts-and-forms/forms-vs-pages-vs-layouts.md.

Nothing in the offline schema shows this, because SLSummary carries only IsApproved. In the live tenant, generating a schedule does not publish it — a three-step workflow named "ASC 842 Schedule Review/Approval" does:

#StepTypeApproval LevelBound form layout
—(submission)Form—ASR Submit ASC 842 Schedules
1Initial Review of ASC 842 SchedulesFormMemberASR Initial Review of ASC 842 Schedule
2Approve ASC 842 Schedules (ASG)FormMemberASR Approve ASC 842 Schedules (ASG)
3Approve ASC 842 Schedules (Client)FormMemberASR Approve ASC 842 Schedules (Client)

The form type carries sequence prefix ASR and declares attachability per entity kind: Portfolio and RE Contract are Yes; Capital Program, Prototype, Location, Parcel, Site, Project, Facility, Capital Project and — ⚠ — Equipment Contract are all No.

Three things follow for a rebuild:

  1. The ASC 842 measurement is a candidate, not a published result. SLSummary.IsApproved is the terminus of a human chain, and it is documented as irreversible once set.
  2. Two parties sign off, ASG then client. A single-approver design is the wrong process.
  3. Equipment leases have no route through this gate, yet they produce ASC 842 schedules — Asset carries the full classification field set and Contract.GenerateFASBSchedule exists on equipment contracts. Unresolved; see open questions.

See ACC-R-060, ACC-R-061, ACC-R-062.

Differences from ContractFinancialTest that matter:

  1. The Cap Lease Test splits Test 5 into 5a and 5b; the ASC 842 test has a single Test 5.
  2. Cap Lease Test 4 is land/building-value based (FMVOfBuilding + FMVOfLand, net of base-year expenses, against AggregateNNNBaseRentNPV); ASC 842 Test 4 is InitialLiabilityBalance vs FairValueControlled × FairValueThreshold.
  3. Cap Lease results are free sTYPE_TEXT; ASC 842 results are sTYPE_PASS_FAIL.
  4. Cap Lease Test has no lock, no AutoComputed, no per-standard measurement, and no child record — it is a flat block of columns on contract_admin.

Derived: this is the ASC 840 capital-lease test, retained for history. A rebuild should carry the data forward for audit but should not implement the logic. Confirm with the client whether any report still reads it.

Open questions

Ranked by how much they block a rebuild.

  1. (new) ⚠ How does an equipment-lease ASC 842 schedule get approved? The review workflow's form type excludes Equipment Contract (ACC-R-061), yet equipment leases generate schedules. Either they bypass the gate or they are approved at portfolio level.
  2. (new) What does each of the four ASR form layouts collect? They define the approval record ASG Edge+ must reproduce, and none has been opened.
  3. (new) What happens on rejection at step 2 or 3? No rollback or re-open path is documented and SLSummary has no "rejected" representation.
  4. What are the values of the Schedule Creation Reason Code table? It is the only field that records why a schedule exists (initial, remeasurement, modification, reclassification, impairment, term shortening…). Without the enumeration, the schedule-version chain cannot be replayed. Check Admin > Manage Firm Drop Downs.
  5. Does ASC 842 Test 4 compare the adjusted or unadjusted initial liability? The vendor text says "Initial Liability Balance (Adjusted)" on ThresholdFairValueControlled but names the field plainly as InitialLiabilityBalance on Test4Result. Open an ASC 842 Test on a contract with a non-zero InitialLiabilityBalanceAdjust and read the on-screen comparison.
  6. Do "Test Begin Date" / "Test End Date" exist in the UI as distinct fields from Topic842BeginDate / Topic842EndDate? TestTermLength's definition names them; the schema does not contain them.
  7. What distinguishes Reclassification* from Reclass* in the roll-forward block? Six fields, two triples, no definitions.
  8. Which impairment input wins when SLSummary.ImpairmentAmount, ContractFinancialTest.ImpairmentsAmount and Asset.ImpairmentOverride are all populated?
  9. Which numbered ExportAcctNNumber slot is which GL concept? Twenty unnamed slots, copied onto every period row. Now scoped to one row: open 842 Rent at FirmCodeEdit.jsp?TableType=2162 and read the twenty values. The cheapest remaining high-value capture in the module.

9b. (new) Why is DontAmortizeAssetValue unchecked on the only configured schedule type? Either ASG amortises the ROU asset on every schedule, or the flag is vestigial. Its behaviour cannot be observed in this tenant either way, which leaves ACC-R-030 permanently Inferred.

  1. What does Covenant.HoldAmountInSchedLiability do? No definition; it is the only Boolean on Covenant that names the schedule liability.
  2. Is Contract.FinalResult (Cap Lease Test group) actually the ASC 842 result? The label and the subgroup disagree.
  3. What is the sign convention on PVOfFinancialTermsWithAdjustments? The vendor text says minus the adjustments; the per-standard fields say with.
  4. Can a contract carry more than one active SLSummary per standard? IsSLSchedule, IsASC842Schedule and IsIFRS16Schedule are three independent Booleans on the same row — nothing in the schema forbids two of them being true at once, nor two active rows of the same kind.
